# Фаза 2 — Экспорт / импорт JSON: план реализации

## Контекст

Фаза 1 закрыта (метры, кольца, `size`). Фаза 2 из `PLAN.md` даёт перенос данных между устройствами и бэкап: всё лежит только в `localStorage` (`src/storage.js`, ключ `daggerheart-tracker-v1`), и потерять его легко. Карт и шаблонов пропсов ещё нет (фазы 3–4), поэтому формат файла их резервирует, а импорт пока работает с монстрами, персонажами и энкаунтерами.

Решения, принятые с пользователем:
- **Бэкап хранит энкаунтеры со ссылками** на монстров библиотеки из того же файла, поэтому после восстановления связь с библиотекой сохраняется. Самодостаточными (с копиями монстров внутри) экспортируются только выбранные энкаунтеры.
- **Персонажи входят в экспорт** отдельным разделом `characters[]` с тем же диалогом конфликтов.

Первым шагом реализации этот план сохраняется в репозиторий как `PHASE2.md` (по аналогии с `PHASE1.md`).

## Что сейчас

- `Encounter = { id, name, entries: [{ adversaryId, count }] }`, монстры берутся только из `state.adversaries` (`App.jsx` `handleDeployEncounter`, `EncounterBuilder.jsx` `nameOf`/карточки).
- Все id выдаются из одного счётчика `state.nextId`, то есть они **уникальны глобально** между монстрами, персонажами и энкаунтерами.
- Токен монстра хранит `refKind: 'adversary', refId`. По нему `BattleSidePanel` ищет статблок только в библиотеке (`BattleSidePanel.jsx:141`).
- Тестов нет, проверка — `npm run build` и ручная.

## Ключевое решение: локальные монстры энкаунтера без миграции хранилища

У энкаунтера появляется необязательное поле `adversaries: []` (локальные монстры). Формат `entries` **не меняется**: `adversaryId` сначала ищется среди `enc.adversaries`, потом в библиотеке. Коллизий нет, потому что при импорте локальные монстры получают новые id из `nextId`. Поэтому не нужно ни поднимать `SCHEMA_VERSION` (это очистило бы доску), ни мигрировать `localStorage`. Переход на `placements` / `ref: { lib } | { local }` из целевой модели делается в фазе 3 вместе с миграцией энкаунтеров.

Хелпер в `src/constants.js`:
```js
export const findEncounterAdversary = (enc, id, library) =>
  enc.adversaries?.find(a => a.id === id) ?? library.find(a => a.id === id);
```

## Формат файла

```js
ExportFile {
  app: 'dh-tracker',          // маркер «это наш файл»
  version: 1,
  kind: 'backup' | 'selection',
  exportedAt: ISO-строка,
  adversaries: [Adversary],   // библиотечные
  characters:  [Character],
  encounters:  [{ id, name, entries: [{ adversaryId, count }], adversaries: [Adversary] }],
  maps: [], propTemplates: [] // зарезервировано под фазы 3–4
}
```
- id в файле — id исходного устройства. Они нужны только для связей внутри файла и при импорте всегда перенумеровываются.
- `backup`: в `adversaries` вся библиотека, у энкаунтеров `entries` ссылаются на неё (и на свои локальные монстры, если они есть).
- `selection`: энкаунтер самодостаточен, все используемые библиотечные монстры копируются в `encounter.adversaries`. Выбранные отдельно монстры идут в верхний `adversaries`.

## Шаги

### 1. `src/transfer.js` (новый, чистые функции без React)
- `EXPORT_VERSION = 1`, `MIGRATIONS = {}` (ключ — версия, из которой мигрируем: `while (v < EXPORT_VERSION) data = MIGRATIONS[v](data)`). Первая реальная миграция появится в фазе 3.
- `buildBackup(state)` и `buildSelection(state, { adversaryIds, characterIds, encounterIds })` → `ExportFile`. Самодостаточный энкаунтер: копировать в `enc.adversaries` каждого монстра, найденного через `findEncounterAdversary`. Записи с удалёнными монстрами отбрасывать.
- `downloadJson(file, filename)`: `Blob` + временный `<a download>`. Имена: `dh-backup-YYYY-MM-DD.json`, `dh-export-YYYY-MM-DD.json`, `dh-encounter-<slug>.json`.
- `parseImport(text)` → `{ file }` или `{ error }`. Проверить JSON, `app === 'dh-tracker'`, числовой `version`. `version > EXPORT_VERSION` даёт ошибку «файл из более новой версии приложения». Затем прогнать `MIGRATIONS` и нормализовать записи через `makeAdversary` / `makeCharacter` / `makeEncounter`, чтобы заполнить недостающие поля. Массивы по умолчанию `[]`.
- `findConflicts(state, file)` → `[{ kind: 'adversary' | 'character', incoming, existing }]`. Конфликт — совпадение имени (trim, без учёта регистра) с записью в библиотеке. Если содержимое совпадает (сравнение без `id`, с сортировкой ключей), это не конфликт: запись молча считается уже существующей. Поэтому восстановление бэкапа поверх свежего SRD-сида не задаёт ~130 вопросов. Локальные монстры энкаунтеров в конфликтах не участвуют.
- `applyImport(state, file, resolutions)` → новый state, чистая функция. `resolutions[kind][fileId]` принимает одно из значений: `'replace' | { rename: string } | 'skip'`.
  - Библиотечные записи: новая или переименованная получает новый id из `nextId`. `replace` переписывает содержимое существующей записи, **её id сохраняется**, поэтому токены и энкаунтеры остаются привязаны. `skip` и совпадение по содержимому ничего не добавляют. Все исходы пишутся в `libIdMap: fileId → appId` (у `skip` — id существующей одноимённой записи).
  - Энкаунтеры добавляются всегда, с новым id. Локальные монстры получают новые id (`localIdMap`). `entries[].adversaryId` переписывается через `localIdMap`, затем `libIdMap`. Неразрешённые записи отбрасываются.
  - Возвращает также сводку `{ added, replaced, renamed, skipped }` для показа пользователю.
- `uniqueName(name, taken)` → `Name (2)`, `Name (3)`… (используется для подсказки при «Переименовать» и для «применить ко всем»).

### 2. `src/App.jsx`
- Reducer: `case 'IMPORT': return applyImport(state, action.file, action.resolutions);`. Импорт атомарный, одним действием.
- `handleDeployEncounter`: искать монстра через `findEncounterAdversary(enc, adversaryId, state.adversaries)`.
- В шапке (GM, на всех вкладках, справа) кнопка **Data**. Она открывает `DataModal` (`useState`, как `modal`).
- В `BattleSidePanel` передать `findAdversary(id)`: ищет в библиотеке, затем в `enc.adversaries` всех энкаунтеров. Тогда у токенов из импортированного энкаунтера виден статблок.

### 3. `src/components/DataModal.jsx` (новый)
Модалка `.modal .modal-wide` с двумя разделами:
- **Экспорт**: кнопка «Экспорт всего (бэкап)». Ниже блок «Выбрать»: три сворачиваемые группы с чекбоксами — Adversaries (с поиском, как в `AdversaryLibrary`, и «все / ничего»), Characters, Encounters. Кнопка «Экспортировать выбранное (N)». Группы Maps / Props добавятся в фазах 3–4.
- **Импорт**: `<input type="file" accept=".json,application/json">` → `file.text()` → `parseImport`. Ошибка показывается текстом в модалке. Затем `findConflicts`, при наличии конфликтов — `ConflictDialog`, потом `dispatch({ type: 'IMPORT', ... })` и сводка «Добавлено: 3 монстра, 1 энкаунтер · заменено 1 · пропущено 2».

### 4. `src/components/ConflictDialog.jsx` (новый)
Конфликты показываются по одному: «“Goblin” уже есть в библиотеке монстров», рядом краткие строки обеих версий (Tier/Type/HP/Diff для монстра, HP/Evasion для персонажа). Кнопки:
- **Заменить**.
- **Переименовать**: поле с подсказкой `uniqueName(...)`, редактируемое; подтверждение недоступно, пока имя занято.
- **Отменить**: пропустить эту запись.
- Чекбокс «Применить к остальным (N)». Для «Переименовать» остальным даётся автоимя.
- Ссылка «Прервать импорт» ничего не меняет.

Компонент обобщён по `kind` (подпись и строка-сводка берутся из словаря), поэтому карты и шаблоны пропсов в фазах 3–4 подключатся добавлением записи в словарь.

### 5. `src/components/EncounterBuilder.jsx`
- `nameOf`, сводка на карточке и `EncounterEditor` используют `findEncounterAdversary`. У локальных монстров pill «local» (из файла, нет в библиотеке).
- При сохранении в редакторе удалять из `draft.adversaries` монстров, на которых больше нет `entries`.
- Пикер `+ Add` по-прежнему добавляет только библиотечных монстров.
- На карточке кнопка **Export**: `downloadJson(buildSelection(state, { encounterIds: [enc.id] }), ...)`. Нужны `adversaries` и `encounters`, они уже приходят в props.
- `REMOVE_ADVERSARY` в reducer не меняется: id уникальны глобально, и локальные записи не затронет.

## Проверка
- `npm run build` проходит.
- `npm run dev`, вручную:
  - **Бэкап туда-обратно**: экспорт всего → в DevTools удалить ключ `daggerheart-tracker-v1` → перезагрузить → импорт. Библиотеки, персонажи, энкаунтеры на месте. Совпадающие с сидом SRD монстры не дают диалогов, энкаунтеры деплоятся и ссылаются на библиотечных монстров (правка монстра в библиотеке видна в энкаунтере).
  - **Энкаунтер с карточки**: Export → удалить из библиотеки одного из его монстров → импорт файла. Энкаунтер-копия содержит этого монстра как «local», в библиотеке он **не** появился, Deploy ставит токены, боковая панель показывает статблок.
  - **Конфликты**: изменить HP у «Goblin» → импорт файла со старым Goblin. Проверить все три варианта: «Заменить» (id прежний, токен на доске показывает новые статы), «Переименовать» (`Goblin (2)`), «Отменить». Затем «применить к остальным» и «Прервать импорт».
  - **Ошибки**: не-JSON, чужой JSON, `version: 99` — понятное сообщение, state не меняется.
  - `?role=player` во второй вкладке после импорта и деплоя показывает те же токены.
